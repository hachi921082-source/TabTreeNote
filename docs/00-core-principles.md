## 1. IPC の `Result<T>` 型規約とエラーコード（PLAN §4.4 / §2 冒頭）

- IPC はすべて `ipcMain.handle` / `ipcRenderer.invoke`（リクエスト/レスポンス）を基本とし、メイン→レンダラの一方向イベントは `webContents.send` + preload 購読関数で扱う。
- 返却は **`Result<T>` 型**（成功/失敗を判別可能な discriminated union）で統一。例外はメイン境界で捕捉してエラーコード化する。

```ts
type Result<T = void> =
  | { ok: true; value: T }
  | { ok: false; error: { code: ErrorCode; message: string; path?: string } };

type ErrorCode =
  | 'NAME_DUPLICATE' | 'NAME_INVALID' | 'NOT_FOUND' | 'IO_LOCKED'
  | 'TRASH_FAILED' | 'DECRYPT_FAILED' | 'CONFLICT' | 'META_CORRUPT'
  | 'LONG_PATH' | 'UNKNOWN';
```

- 定義場所: `src/main/util/result.ts`（実装）/ `src/shared`（型）。全型定義は [data-model.md](data-model.md) §4 参照。

## 2. アトミック書き込みパターン（PLAN §5.2 / §3 `atomicWrite.ts`）

永続化を伴う保存はすべて `atomicWrite`（`src/main/fs/atomicWrite.ts`）を経由する。順序:

1. **temp ファイル（プレフィックス付き）へ書込** → 2. **fsync** → 3. **（世代スワップを末尾に集約）旧 target を `.bak` へ rename** → 4. **temp を target へ rename**

各操作は `retry`（EBUSY/EPERM 対策、下記 §7）を適用する。

- **順序の意図（クラッシュ耐性）**: 世代スワップ（`.bak` 退避と target 置換）を末尾に集約することで、temp 書込中（メモが大きいほど長い）にクラッシュしても live な target は無傷（復旧不要）。target 不在の窓は 2 つの rename の間の一瞬に限定され、そこでクラッシュしても target か `.bak` のいずれかが必ず存在する。逆順（先に `.bak` 退避してから temp を書く）は target 不在の窓が広がるため採らない。
- **ディレクトリ fsync は行わない（v1・NTFS 前提, Fix6）**: rename 後のディレクトリエントリ自体への明示的 fsync は行わない（NTFS のメタデータジャーナリングに委ねる）。temp ファイル本体への fsync は実施する。ext4 等 POSIX 環境対応は将来検討。
- **対象範囲**（DESIGN §2.6）: メモ本文 `.txt` / 暗号化メモ `.txtenc`（`.bak` も暗号化済みで平文は残らない）/ タブ単位メタ JSON / アプリ設定 JSON。**直近 1 世代のみ**の `.bak`（次回保存時に上書き）。
- 詳細な理由: DESIGN §2.6 / PLAN §5.2。

## 3. 実ファイルとメタ JSON の同期順序（DESIGN §3.2 / PLAN §5 冒頭・§5.3）

実ファイルとメタ JSON の**両方に影響する操作**（リネーム・移動・コピー・複製）は次の順序で行う:

1. **① ストア更新**: メイン側メタ表現上で参照（ファイル名・ツリー順序・階層）を新状態へ書き換える（この時点でディスクのメタ JSON はまだ書き換えない）。重複チェック・サニタイズを先に実施し、NG なら即エラー返却してファイル操作しない。
2. **② 実ファイル操作**（`fs.rename` 等）+ **予約テーブル登録**（自己発火除外のため `selfWriteRegistry` へ登録、下記 §4）。`retry` 適用。
3. **③ 実ファイル操作成功の直後にメタ JSON をアトミック保存**（§2 の `atomicWrite`）。

- この順序で実ファイル操作からメタ永続化までの時間差を数ミリ秒に抑える。
- **極稀にこの隙でクラッシュした場合**: メタ破損復旧カスケード（§9）が安全網。メモ本体は失われないが、ツリー構造情報を失う可能性がある**受容済みトレードオフ**（DESIGN §3.2 / PLAN §8-6）。

## 4. 自己書き込み予約テーブル（selfWriteRegistry）の一元化（PLAN §5 冒頭・§5.6 / DESIGN §3.3）

アプリ自身が行う FS 操作は監視イベントを誘発する。これを「外部からの本当の変更」と誤認しないため、**アプリ発のあらゆる FS 操作**を実行前に `selfWriteRegistry`（`src/main/watch/selfWriteRegistry.ts`）へ登録し、対応する監視イベントを自己発火として破棄する。

- **予約登録は fs 層に一元化する**（呼び出し側任せにしない = 登録漏れ=外部変更の誤検知を防ぐ）:
  - `atomicWrite` が、`.bak` へ退避する旧 target と最終 target の**両方のパスを自身で登録**してから rename する。temp はプレフィックス `ignored` 除外でイベントが出ないため登録不要。
  - メモ本文・メタ JSON・アプリ設定 JSON の保存はすべて `atomicWrite` 経由なので自動的に予約登録を通る。
  - rename/unlink/trash（`memoFileService` / `trash.ts`）も fs 層ラッパ内で対象パスを登録してから操作する。
- **対象操作**（DESIGN §3.3 包括原則）: アトミック書き込み / `.bak` 生成 / メモ・タブのリネーム・AutoReName / ごみ箱送り・直接削除 / 暗号化変換時の平文原本削除 / DND のタブ間移動・コピー・複製。
- **予約レコードの寿命 = ハイブリッド方式（TTL + 即時クリア）**（PLAN §5.6）:
  - **マッチしたら即時クリア**: 対応 chokidar イベントを 1 回消費した時点でレコードを即座に削除（同一パスへの以後の真の外部変更を誤判定しない）。
  - **TTL フォールバック（既定 2–3 秒）**: 対応イベントが発火しなかった場合の肥大化防止。chokidar デバウンス（100–300ms）より十分長く、Windows の I/O バッファリング遅延（数十〜数百 ms）に余裕を持たせる。

## 5. 競合判定の 2 系統（判定基準が異なる — PLAN §5 冒頭）

変更検出の判定材料が用途により異なる。この非対称性は意図的なもの。

- **保存 API の競合チェック（`memo:save` / `crypto:saveEncrypted`）= ハッシュ比較のみ**: 保存操作の実行時点で現在のディスク実体のハッシュを計算し、レンダラ保持の `expectedHash` と一致するか一発判定する（mtime/サイズは見ない）。不一致なら `evt:conflict` 発火・保存中断。
- **ファイル監視側（自己発火判定・外部変更検知）= mtime + サイズ + ハッシュの複合判定**: 継続監視の中で自己書き込み由来イベントの除外精度を上げるため複数材料を照合する。

## 6. hash フィールドの対象（PLAN §4.4 / Fix4 / `util/hash.ts`）

- hash 系フィールドはすべて「**ディスク上の実ファイルの内容そのもの（ファイル全体のバイト列）のハッシュ**」。平文本文のみ・`.txtenc` の暗号文部分のみのハッシュではない。
- `.txtenc` は JSON ヘッダ（`hint` 等）を含む**ファイル全体**が対象なので、hint 変更のようなヘッダ部分の変更も競合として検出できる。
- 実装場所: `src/main/util/hash.ts`。

---

## 7. Windows ロックエラーのリトライ方針（DESIGN §3.3 / PLAN §6 / `fs/retry.ts`）

- Windows ではウイルス対策ソフト/インデックスサービスがファイル作成・変更直後に一時ロックし、`fs.rename`/`fs.unlink`/書き込みが `EBUSY`/`EPERM` 等で失敗し得る。
- **書込・rename・削除の各操作に短いリトライ**（例 **3–5 回, 50–200ms バックオフ**）を挟む。全滅時のみ `IO_LOCKED` をユーザー表示。
- 実装場所: `src/main/fs/retry.ts`。

## 8. エラーハンドリング表（PLAN §6 全体を転記）

| 事象 | 方針 | 参照 |
|------|------|------|
| Windows ロック（EBUSY/EPERM 等） | 書込/rename/unlink に短いリトライ（例 3–5 回, 50–200ms バックオフ）。全滅時のみ `IO_LOCKED` をユーザー表示 | §3.3 |
| ごみ箱送り失敗（ネットワークドライブ/権限） | `TRASH_FAILED` → `evt:trashFallback` でUI に「直接削除しますか？」確認。**承諾時のみ** `memo:delete` を `forceDirect:true` で再 invoke し `fs.unlink` 相当で直接削除。`forceDirect` 無の再試行では再びごみ箱を試みるだけなので失敗ループにならない。無確認削除しない | §2.6 |
| メタ JSON 破損 | 復旧カスケード（`.bak`→フラット再生成→通知）。メモ本体は決して失わない | §3.2/§5.7 |
| アプリ設定 JSON 破損 | 同様にアトミック保存+`.bak`+復旧。全滅時は既定設定で再生成し通知 | §3.2 |
| 暗号復号失敗（誤 PW/改ざん） | 認証タグ検証失敗を `DECRYPT_FAILED`。「パスワードが違います」。本文は一切返さない | §2.9 |
| 外部編集競合 | mtime+サイズ+ハッシュで判定。編集中なら `evt:conflict`、解決ダイアログ中は自動保存/入力ロック | §3.3 |
| 名前重複/禁止文字 | ファイル操作前に検出しブロック（`NAME_DUPLICATE`/`NAME_INVALID`）。実ファイルは触らない | §2.1/§3.1 |
| 保存中クラッシュ | atomicWrite は「temp 書込→fsync→旧 target を `.bak` へ rename→temp を target へ rename」の順（世代スワップを末尾に集約, §5.2）。temp 書込中クラッシュでも **live target は無傷**、世代スワップ中クラッシュでも target か `.bak` のいずれかが必ず存在。暗号変換は `.txtenc` 永続化後に平文削除で平文喪失を防止 | §2.6/§2.9 |
| 長パス | `LONG_PATH` 警告。v1 は正式対応外 | §4 |
| 予期せぬ例外 | IPC 境界（`ipcMain.handle`）で必ず catch し `Result{ok:false, code:'UNKNOWN'}` 化。プロセスは落とさない。**レンダラへ返す `Result` エラーは `code`/`message`/`path?` のみに留め**（内部情報を UI へ露出しない）、**元の OS エラーコード（`err.code`）・例外名・スタックはメインプロセス側の内部ログにのみ記録する**（Fix8, §10） | §6 |

## 9. メタ破損復旧カスケード（DESIGN §3.2 / PLAN §5.7）

読み込み時にパースエラー等で破損を検知したら次の順で復旧:

1. 直近 `.bak`（メタの世代バックアップ）があれば読込を試行 → 成功すれば採用。
2. 失敗/`.bak` 無し → フォルダ直下実ファイル（`.txt`/`.txtenc`, 直下のみ, リンク無視）から**フラット構造でメタ再生成**（順序=名前順等の既定、階層/ラベルは失う）。
3. `evt:metaRecovered` でユーザーへ「メタ情報を再構築しました」と通知。再生成メタは次回アトミック保存で永続化。

- **堅牢性の中核原則**: メタ情報が失われても、**メモ本体（`.txt`/`.txtenc`）は決して失われない**（DESIGN §3.2）。
- 「正常だがファイル 1 件参照欠落」の部分修復は行わない（対応不要）。

## 10. セキュリティ不変条件と内部診断ログ方針（PLAN §6 末尾 / Fix8）

**セキュリティ不変条件**（実装で常に保証）:
- 鍵/パスワードはメインに閉じ**レンダラへ渡さない**。
- 復号平文を**ディスクへ書き出さない・インデックスに入れない・内部ログにも出さない**。
- 外部起動は OS 標準 API（`shell.openPath`/`shell.openExternal`）のみで**シェル文字列連結しない**。
- `contextIsolation:true` / `nodeIntegration:false` / `sandbox:true` / preload は限定 API のみ公開。

**内部診断ログ方針（Fix8）**:
- `Result` のエラーオブジェクトはレンダラ向けに `code`/`message`/`path?` のみを保つ（診断詳細を UI/レンダラへ公開しない）。
- 障害解析のため**メインプロセス側の内部ログ**（`console.error` またはログファイル等、出力先は developer 判断）には、捕捉した例外の**元の OS エラーコード（`err.code`）・例外名・スタックトレース**を記録する。特に `UNKNOWN` へ丸めた例外は丸める前の生情報を必ず残す。
- **鍵・パスワード・復号平文は内部ログにも出力しない**（セキュリティ不変条件を内部ログでも順守）。

## 11. 名前サニタイズ / バリデーション（PLAN §5.9 / DESIGN §3.1 / `fs/pathSafety.ts`）

- 入力/リネーム時に **Windows 禁止文字**（`\ / : * ? " < > |`・制御文字）、**予約名**（`CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`）、**前後空白・末尾ピリオド**を検出。
- **リアルタイム表示**: レンダラ入力欄で即時バリデーションメッセージ。`/` 等は `-`/`_` への置換候補をワンクリック提示（DESIGN §3.1 UX）。
- **タブ名は重複禁止**（大文字小文字・正規化後で比較, DESIGN §2.1）。**メモ名は同一タブ内で `.txt`/`.txtenc` 統一空間で重複禁止**（DESIGN §3.1）。表示名とファイル名は分離しない（入力段階でサニタイズ）。
- **長パス**（絶対パスが 260 文字超）を検出したら `LONG_PATH` として警告（v1 は正式対応せず既知の制限, DESIGN §4）。
- 実装場所: `src/main/fs/pathSafety.ts`（メイン側検証）+ レンダラ入力欄の即時バリデーション。
