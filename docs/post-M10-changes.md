> password lock + Markdown live preview) reached implementation completion. Handled through direct
> chat dialogue rather than a formal milestone plan (`PLANv3.md`), mirroring the role
> [post-M7-changes.md](post-M7-changes.md) plays for the v1 scope. Written in English per user
> request (2026-07-28); v1/v3 design docs and other project docs remain Japanese.

## Spec changes / new features (design phase, 2026-07-27–28)

### Node lock (v3 M8 feature) refinements

All three items below originate from the same user design-reconsideration request and were evaluated/written up by designer in `docs/v3/DESIGNv3.md` (§1.14, §1.15, and the `§5` "第5回" decision-log entry). **§1.14 and §1.15 are now implemented — see below.**

- **New "permanently remove node lock" operation** (`docs/v3/DESIGNv3.md` §1.14). **[Implemented, 2026-07-29 — verified by reviewer-lite, done]**. Currently, once a node is locked there is no way to permanently strip the lock and restore the subtree to fully normal, unencrypted, freely-movable status — the only paths are toggling locked/unlocked-session or full deletion (the "one-way vault" rule, §1.12). User requested an explicit, deliberate escape hatch for this, distinct from the existing temporary-session unlock. Designer concluded this is safe (the one-way-vault rule was adopted specifically against *accidental drag-and-drop* exposure risk, not against deliberate permanent unlocking) and designed it as a mirror of the existing `lockNode` flow: new context-menu item → irreversible confirmation dialog → mandatory password re-entry (no session-key reuse, same discipline as `crypto:decryptMemoToPlain`) → new IPC `crypto:removeNodeLock(tabId, memoName, password, lockContext?)` → decrypts the whole subtree back to plain `.txt`/`.md` files with original names, splices them back into the normal meta tree. Nested (still-locked) descendants are promoted as opaque, still-locked blackboxes rather than being force-decrypted. New error code: `NAME_DUPLICATE` (name collision on restore, same all-or-nothing pre-check pattern as `moveIntoSession`). Both the existing temporary-session "ロックを解除" and the new permanent "ロックを完全に解除する" stay as separate menu items (user-confirmed, not just designer default) — the M9a–M9c session mechanism is unaffected.
  - Estimated cost: medium — smaller than M9a (nested-lock support), roughly on par with a partial M8-sized feature addition. No new persisted data structures needed (`NodeLockBlob`/`NodeLock`/`TreeNode` already have the fields required); mostly one new function in `nodeLock.ts` (~150–250 lines), one IPC channel, and menu/dialog wiring, reusing existing building blocks (`lockNode`'s conversion loop, `crypto:decryptMemoToPlain`'s re-auth discipline, `moveIntoSession`'s collision pre-check, `persistNodeLockSession`'s ancestor recursion, `deleteNodeLockSession`).
  - **Implementation note**: during implementation, `developer-lite` found a genuine ambiguity in this section's text (generic "write real `.txt`/`.md` files" wording for the restore step vs. the nested-lock paragraph's explicit "never touches plaintext on disk" guarantee). Escalated to `designer-lite`, who confirmed the nested-target case must re-encrypt in place under the parent session's key rather than writing plaintext, and fixed this section's wording accordingly. Implemented behavior matches that resolution; `reviewer-lite` confirmed via on-disk byte comparison that nested removal changes the `.txtenc` in place with no new plaintext file created, while top-level removal correctly writes real plaintext files.
  - **Known pre-existing bug found during verification (out of scope, not fixed)**: unlocking a *nested* lock via the existing "ロックを解除" menu item fails with `NOT_FOUND` — `Tree.tsx`'s `onSelect` for the locked-placeholder row never passes `lockContext`, so `crypto:unlockNode` always searches the top-level tab meta tree instead of the parent session's `children`. Pre-dates this change; worth a small follow-up fix at some point.

- **Block deletion of a still-locked (no-session) node** (`docs/v3/DESIGNv3.md` §1.15). **[Implemented, 2026-07-29 — verified by reviewer-lite, done]**. Currently `Tree.tsx` (~L386–396) always shows a "削除" (delete) item on a locked node's context menu alongside "ロックを解除", even for a single selection — letting anyone delete a password-protected subtree without ever proving they know the password. (The nearby code comment claiming "single-select shows only unlock" is stale/inaccurate — the actual code always adds delete too; confirmed not intentional.) User wants this delete path removed; deletion of a locked subtree should require going through one of the two unlock paths first.
  - Multi-select case: if **any** item in the current selection resolves to a still-locked node — not just the right-clicked row — designer decided to **reject the entire batch delete**, not silently skip the locked member(s). Reasoning: consistency with this codebase's existing all-or-nothing batch conventions (`moveIntoSession`'s name-conflict rejection, `tree:updateStructure`'s duplicate check), and because locked nodes are invisible-by-design (§1.2), so a silent partial-skip risks the user not noticing fewer items were deleted than requested.
  - Found and documented an existing implementation-correctness gap while at it: `Tree.tsx` currently only inspects the right-clicked row's `nodeLocked` flag, not the full `selection.selected` set — so a normal row right-clicked within a mixed selection could currently let a hidden locked node slip into a batch delete today. This needs fixing as part of the same change. Fixed via a new `multiSelectionHasLockedNode` helper that scans the full selection.
  - New backend defense-in-depth check added in `memo:delete`'s non-`lockContext` branch, with new error code `NODE_LOCKED` (distinct from the existing move/copy-specific `LOCK_BOUNDARY_VIOLATION`); `reviewer-lite` confirmed this rejects a locked target even when called directly via IPC, bypassing the UI's menu-hiding.
  - Explicit tradeoff noted and accepted per user's explicit instruction: this removes the previously-possible (if undocumented) escape hatch of deleting a locked placeholder without its password — e.g. abandoning a subtree whose password was genuinely forgotten. An unofficial workaround remains (deleting the raw obfuscated `.txtenc` file directly via Explorer; the existing meta-reconciliation fallback tolerates this). No new "shred without password" feature was added to compensate.
  - Estimated cost: small, additive on top of the §1.14 estimate above — UI-side menu/selection-guard logic in `Tree.tsx`, one upfront batch-rejection check in `memoHandlers.ts`'s `memo:delete`, one new error code. No new IPC channel or persisted structure.

### Lock-while-memo-is-open UX friction

**[Implemented, 2026-07-29 — verified by reviewer-lite, done]**. Previously, `handleRequestLockNode` (`App.tsx` ~L1264–1277) fully blocked the "サブツリーをロック" action with a status message ("ロック対象のメモが開いています。先に閉じて…からロックしてください。") if the target node or any descendant was open in the editor — the user had to manually switch away first. This was a developer-level implementation guard, not a hard requirement from `DESIGNv3.md`/`PLANv3.md`. User found this cumbersome and asked whether it could instead auto-close the editor first.

Fix applied: reuses the exact pattern already used by the existing M6 "ロック" button (`handleLockMemo`, `App.tsx` ~L1196–1210) when locking a currently-open encrypted memo — calls `requestCloseCurrentMemo()` (handles unsaved-edit confirmation/auto-save) then explicitly clears editor state (`setOpenMemo(null)`, `setContentLF('')`, `setDirty(false)`, `setEditorStats(null)`, `setConflictInfo(null)`, `reportActiveMemo(null)`) before proceeding with the lock; aborts the same way `handleLockMemo` does if the user cancels an unsaved-changes prompt. `reviewer-lite` verified target-node-open and descendant-open cases, both with and without unsaved edits, plus cancel-aborts-lock and confirm-then-proceeds-after-save, and a negative check that locking an unrelated subtree doesn't touch an unrelated open memo.

**Minor stale comment found during verification (not yet fixed)**: the comment directly above `handleRequestLockNode` (`App.tsx` ~L1265–1266, "dirty ガードは対象外...") predates this fix and no longer matches the code, which now does perform a dirty-aware auto-close.

### Markdown live preview decoration bugs (M10b) — found via focused tester bug hunt, 2026-07-28

User reported 3 symptoms while using the live-preview decoration feature: stray `</span>` text leaking into the document, the decoration toolbar sometimes seeming absent, and being unable to turn bold back off. A tester pass scoped specifically to this feature (excluding image paste, per user instruction) reproduced 2 of the 3 with clear root causes; the "toolbar absent" report turned out to be a distinct, separate finding (see the toolbar item below) rather than the toolbar literally failing to render.

- **Bug A — stray `</span>` leaks as literal text** (`src/renderer/editor/decorationCommands.ts`, `src/renderer/editor/markdownDecorations.ts`). **[Implemented, 2026-07-29 — verified by reviewer-lite across 3 fix rounds, done]**. 100% reproducible: decorate a range (e.g. color "abc"), then select only a *subset* of that already-decorated range (e.g. just "b") and apply a second decoration (e.g. bold). `detectSurroundingSpan()` (`decorationCommands.ts:50-67`) only recognized an existing wrap when the selection boundary exactly matched the tag boundary, so a subset selection created a malformed nested span (`<span style="color:...">a<span style="font-weight:bold">b</span>c</span>`). `markdownDecorations.ts`'s non-greedy `SPAN_PATTERN` (line 19) then only matched through to the first (inner) closing tag, so the real outer `</span>` rendered as literal text in preview.
  - **Fix, round 1 (2026-07-28)**: replaced `detectSurroundingSpan()` with a general overlap-safe segment split/merge algorithm in `decorationCommands.ts` (`splitIntoSegments`/`applyOrToggleSpanStyle`), and factored the span-matching regex into a new shared module `src/renderer/editor/markdownSpanParser.ts` (`findSpans`) so `decorationCommands.ts` and `markdownDecorations.ts` always agree on exactly what counts as an existing span. The new algorithm finds every existing span overlapping the selection, splits the affected region into segments at both selection and span-content boundaries, applies the toggle only to the in-selection segments, and regenerates flat (never nested) `<span>` tags — merging adjacent same-style segments as a hygiene optimization. While implementing, found and fixed an additional related defect (not in the original diagnosis): the segment/region computation needs to include each touched span's full tag markup extent (not just its content), otherwise unwrapping a span whose content exactly matches the selection left the surrounding `<span>`/`</span>` tag characters untouched outside the replace range. Verified via a standalone esbuild-bundled Node harness against 8 scenarios plus a `findSpans()` round-trip check.
  - **Reviewer-lite round 1 finding (2026-07-28) — regression**: original repro (bug above) confirmed fixed, and Bug B / toolbar single-span cases passed, but a *new* corruption path was found: the segment-merge hygiene step only checked style equality, not textual contiguity (`last.to === seg.from`), so it could splice two non-adjacent segments (separated by an excluded tag-markup region, when a selection spans ≥2 pre-existing spans) together whenever their post-operation styles happened to match — reintroducing the exact "stray `</span>` leaks as text" symptom via an everyday action (e.g. select text spanning 3 spans, clear color). Also caused silent partial application (only the first of several touched segments got the operation, rest silently untouched) in a related case.
  - **Fix, round 2 (2026-07-29)**: added `last.to === seg.from` as a required condition before merging two segments in `applyOrToggleSpanStyle`, alongside the existing style-equality check. Verified by temporarily reverting just this check and confirming the harness reproduced both round-1-finding symptoms exactly, then restoring the fix and confirming all cases pass with well-formed, fully-applied output. `npm run typecheck`/`npx electron-vite build` clean.
  - **Reviewer-lite round 2 finding (2026-07-29) — deeper, pre-existing blocking issue (not introduced by round 2's diff)**: the round-2 contiguity fix is correct and verified in isolation, but the originally-requested repro steps (select text spanning multiple existing spans, e.g. via Ctrl+A or a normal mouse drag in preview mode, then apply/clear a decoration) **still fail — as a silent total no-op**, for a different root cause in the same file. `splitIntoSegments` (`decorationCommands.ts:103-143`) only recognizes selection boundaries that land on an existing span's *content* edge (`contentFrom`/`contentTo`); a boundary landing on the span's *outer tag-markup* edge (`span.from`/`span.to`) is treated the same as an unsupported "boundary inside raw tag text" case and the whole operation is silently discarded (`newFromOffset`/`newToOffset`, lines 222-247, fall through to what the code's own comment calls a "theoretically unreachable" fallback — it is in fact reached). **This matters because CodeMirror's decoration widgets are atomic for position-resolution purposes, so a normal mouse drag-selection in preview mode that starts/ends adjacent to a decorated span snaps to the span's *outer* edge, not its content edge — meaning this is the default, essentially only way a real user selects across multiple decorated spans with the mouse.** Regression sanity checks (Bug B toggle-off, single-span toolbar ops, plain-text-adjacent-to-two-spans with content-edge-only selection) all still PASS; only the outer-edge multi-span-boundary case is broken. **User decision (2026-07-29): pause here, do not continue to a round 3 fix yet — resume later.**
  - **Fix, round 3 (2026-07-29)**: added `outerFrom`/`outerTo` tracking to segments so a selection boundary landing on a span's outer tag edge is recognized as "this whole span is inside the selection" rather than an error case, and offset-recovery (`newFromOffset`/`newToOffset`) now checks these before falling back to the content-edge check. Composes correctly with round 1 (overlap-safe split) and round 2 (contiguity check) without touching either. Per explicit user instruction to reduce token cost, verification for this round leaned on developer-lite's own pure-logic Node/esbuild harness (no Electron) rather than relying on reviewer-lite's expensive runtime pass to iteratively find remaining gaps: **21/21 harness cases passed**, exhaustively covering the boundary-condition space (content edge / outer edge / mid-raw-tag / plain-text-adjacent, ×1/2/3 spans, ×apply/clear) plus regression re-runs of rounds 1 and 2's repro cases.
  - **Reviewer-lite round 3 verification (2026-07-29, capped to exactly one round per explicit user instruction) — PASS, approved as done**: verified in the real Electron app (not just the harness) — Ctrl+A across 3 spans + apply/clear both correct; a **genuine CDP-simulated mouse drag-selection** landing precisely on the outer tag edges (the actual real-world trigger, not just Ctrl+A) correctly applied font-size to all 3 segments; all regression spot-checks (Bug B, single-span ops, round 1/2 repros) passed; typecheck/build clean; no console/main-process errors. **Bug A is now considered fully fixed and verified — this closes out the entire "Markdown live preview decoration bugs" item (Bug A + Bug B + toolbar buttons + native menu removal all done).**
- **Bug B — bold cannot be turned off while in preview mode** (same two files). **[Implemented, 2026-07-28 — pending reviewer-lite/tester verification]**. Reproducible: a decorated span renders as `<span class="md-decoration" contenteditable="false">` in preview mode. Double-clicking it to select the text for un-decorating gave CodeMirror a bogus/collapsed selection (it cannot resolve a real document position from a selection anchored inside this opaque contenteditable=false widget), so `runDecorationCommand` never received the correct range. Since bold had no dedicated "clear" branch, this always took the "wrap new span" path and further corrupted the markup (color's clear variant no-op'd silently instead — less destructive, still buggy).
  - **Fix**: `markdownDecorations.ts`'s decoration widget now stores its own generation-source content range (`contentFrom`/`contentTo`, already known from the regex match) and exposes it via `data-decoration-from`/`-to` attributes on its DOM node. A new `EditorView.domEventHandlers({ mousedown })` extension intercepts clicks landing inside any decoration widget and directly dispatches a CodeMirror selection covering that exact source range, bypassing the browser's native (unreliable, for this opaque DOM) selection resolution entirely — confirmed via the CodeMirror 6 API docs that returning `true` from a `domEventHandlers` handler fully preempts CM's own built-in mousedown/selection handling. Combined with Bug A's generalized overlap detection, the pre-existing (already correct) same-value toggle logic now reliably reaches a real, correct range, so bold/color/font-size clearing all work without needing a separate dedicated "clear" branch for bold.
  - **Known residual limitation (documented, not fixed)**: clicking a widget selects its *entire* content range as one atomic unit; sub-selecting only part of an already-decorated range while in preview mode is not supported (switch to source mode for that, per the app's existing "advanced escape hatch" design, DESIGNv3 §2.1). Also, in the rare case where a single drag selection spans two adjacent, differently-styled spans and the toggle causes their styles to diverge partway through, the restored selection may include a few characters of newly-inserted tag markup (cosmetic only — the underlying document text produced is always well-formed, verified by the round-trip check above). Neither of these could be verified against the real Electron UI in this pass (no DOM/Electron available to this implementer) — only reasoned through the documented CodeMirror 6 event-handling semantics and the pure-logic test harness described above.
- **"Toolbar missing" report — clarified, not a rendering bug**. **[Investigated — reclassified as a UX/scope gap; resolved below]**. Tester could not reproduce the toolbar *row* (Markdown label / preview-toggle / `.txt` conversion button) failing to render across several scenarios (new `.md` memo, `.txt`→`.md` conversion, memo switching, tab switching); the user's own screenshot confirms that row does render correctly. Follow-up with the user clarified what was actually meant: they expected **decoration buttons (text color / bold / font size) inside the toolbar**, which had never existed there — decoration commands were only reachable via the **native OS right-click context menu** inside the editor (`Menu.buildFromTemplate().popup()` in `src/main/index.ts`), which the user had never discovered.

**User's requested resolution (2026-07-28) — implemented together with Bug A/B in the same pass**:
- Added text-color (5 fixed swatches + "clear"), bold (toggle), and font-size (3 fixed sizes + "clear") decoration buttons directly to `MarkdownToolbar` (`src/renderer/components/Editor/MarkdownToolbar.tsx`), reusing the same color/size values the removed menu offered. Buttons call `runDecorationCommand` directly through the existing `CodeMirrorEditorHandle` ref (same-process call, no IPC needed) via a new `onDecorate` prop wired in `App.tsx`.
- Removed the native OS right-click context menu's decoration submenu (`src/main/index.ts`) entirely, and removed the now-dead `{ kind: 'decoration' }` variant from `EditorMenuCommandPayload` in `src/shared/ipc-contract.ts` (the `MarkdownDecorationCommand` type itself is retained — it's still used by `decorationCommands.ts`, `CodeMirrorEditorHandle.runDecorationCommand`, and the new toolbar buttons, just no longer routed through IPC).
- The toolbar buttons act on whatever the current CodeMirror selection is, which (per the Bug B fix above) is now correctly resolved even when it touches an existing decoration in preview mode — the same fix benefits both the removed right-click path and the new toolbar path since both ultimately call the same `runDecorationCommand`.
