## 1. 機能1: ノード（サブツリー）単位のパスワードロック

既存の「編集ロック」(`MetaTreeNode.locked`、パスワード不要・本文編集のみ禁止でリネーム/削除は対象外)とは別物。以後、本機能を指して単に「**ノードロック**」と呼ぶ（`locked` フィールドの編集ロックとの混同を避けるため、型・IPC上も別名にする）。

> **フィールド名の確定（developerからのPLANv3/M8内部矛盾指摘への回答、2026-07-25追記）**: 実行時 `TreeNode`（`src/shared/models.ts`）は既に編集ロック用の `locked?: boolean` を持つため、ノードロックの「ロック中(セッション無し)の起点ノードを示すマーカー」を同名 `locked?: true` として追記すると型が衝突する。**正式なフィールド名は `nodeLocked?: true` とする**（`lockToken?: string` は既存に無い名前のため変更なしでそのまま使う）。これは PLANv3.md §4 および `M8-node-lock-core.md` の「このフェーズで扱う型/データ構造」に記載された `TreeNode.locked?: true` のスケッチを訂正するものであり、本注記（DESIGNv3.md側）が正（本ドキュメント冒頭の「PLANv3.mdと齟齬がある場合はDESIGNv3.md優先」の原則通り）。`MetaTreeNode.lock?: NodeLock`（§1.6、ブロブ本体を保持する永続化フィールド）は既存フィールドと衝突しないため変更なし。

### 1.1 対象・強さ（確定）

- **対象**: ツリー内の任意のノード1つとその配下全体。葉メモ単体（子なし）でも、子を持つ枝でも同じ仕組みで適用できる。
- **制約の強さ＝強い制約**: ロック中は配下への新規作成・削除・リネーム・移動・コピー等、あらゆる構造変更操作を禁止する（既存の「編集ロック」が本文編集のみを禁止するのと異なり、ノードロックは配下ツリー全体を丸ごと凍結する）。
- **本文の秘匿**: 既存M6暗号化（`AES-256-GCM` + `scrypt`, `.txtenc`）をそのまま流用。ロック対象配下の全メモを `.txtenc` 化する。
- **ロック対象ファイルの範囲（レビュー指摘反映・明確化）**: 本アプリはツリーの子を持つノードであっても必ず実ファイル（本文）を持つ（「ツリー階層は論理構造、実ファイルはフォルダ直下にフラット」という既存原則の帰結。子を持つ「フォルダ専用の空ノード」という概念は存在しない）。したがって**起点ノード自身の実ファイルも含めて**ロック対象とする（配下だけでなく起点ノード自身の本文・ファイル名も暗号化・難読化される）。例: `Project`（本文あり）の配下に`A`・`B`がある場合、`Project.txt`・`A.txt`・`B.txt`の3ファイル全てが`.txtenc`化＋難読化名リネームの対象になる。
- 本機能は「今の暗号化メモ機能に “名前も隠す” オプションを足す」形の自然な拡張として位置づける。

### 1.2 ロック対象ノード自身の秘匿範囲（確定）

- ロック中はツリー上に「🔒(ロック中)」という**中身の見えないノード1つだけ**を表示する。これは**ロック対象ノード自身の名前も含めて秘匿する**ことを意味する（子の名前だけでなく、ロックの起点ノード自身の元の名前も画面上には一切表示しない）。
- したがって、ロックされたノードを永続化するメタ表現は、通常の `MetaTreeNode`（`memoName` に実名を保持）ではなく、**実名を含まない専用の永続化ノード**として扱う（§1.6 参照）。

### 1.3 名前・階層構造の秘匿（新規部分・確定）

- ロックしたノードの子ノード一覧（名前・階層・順序・ラベル等の `MetaTreeNode` 相当情報）は、メタJSON内で平文保持せず、**暗号化した1つのブロブ**として格納する。
- ブロブの中身は「ロック対象ノード自身の元の表示名」＋「配下の子ツリー構造（既存 `MetaTreeNode[]` 相当。ただし各ノードの `memoName` は実名のまま保持してよい＝ブロブ自体が暗号化されているため内部は平文表現で構わない）」＋「本来の名前↔実ファイル名（難読化名）の対応表」を含む。
- パスワードで復号して初めて、配下の名前・構造がツリー上に展開される（＝ロック解除セッション、§1.5）。

### 1.4 ディスク上のファイル名の秘匿（確定）

- ロック対象（起点ノード自身＋配下全メモ）の実ファイルは、無作為な名前へリネームする（例: `a3f9c1e2b7d4e6f1a2b3c4d5e6f7a8b9.txtenc`）。命名規則は既存の一時ファイルプレフィックス等と衝突しない16進数文字列とし、**`crypto.randomBytes(16).toString('hex')`（128bit）を使う**（レビュー指摘反映: 64bitでも通常十分だが、コストがほぼ変わらないため最初から128bitにして衝突耐性を上げておく）。同一フォルダ内での衝突が発生した場合は再生成する。
- 「本来の名前↔実ファイル名」の対応表は §1.3 の暗号化ブロブに含めて持たせる（ブロブ外・平文では一切保持しない）。

### 1.5 復号方式＝常駐セッション方式（確定・重要な設計判断）

- ロック解除時に**ファイル名を元に戻す（リネームし直す）操作は行わない**。既存の `crypto:open` と同じ考え方で、**ディスク上は常に難読化された名前のまま**にし、アプリ側がロック解除中だけメインプロセスのメモリ上に「本来の名前↔実ファイル名」の対応表（および復号済みの子ツリー構造）を保持する（以下「**ロックセッション**」）。
- ロックし直す操作（再ロック）は、メモリ上のロックセッション（対応表・復号済み構造）を破棄するだけで、ファイル名を難読化名から戻す操作は発生しない。
- **採用理由**: リネームを往復させる方式は、途中クラッシュ時に「一部は元の名前、一部は難読化名のまま」という半端な状態が残るリスクがある。これは本アプリの「アトミック書き込み・同期順序厳守」という既存の安全設計思想（[00-core-principles.md](../00-core-principles.md) §2〜§4）と相性が悪いため不採用とする。
- **セッション中の構造変更の永続化タイミング（確定・developer判断）**: ロックセッション中に配下で行われる構造変更（子メモの新規作成・リネーム・削除・移動・コピー、および**起点ノード自身のリネーム**）は、既存の同期順序原則（[00-core-principles.md](../00-core-principles.md) §3: ストア更新→実ファイル操作→直後にメタJSON永続化）と一貫させるため、**操作の都度、ロックセッションが保持する鍵で子ツリー構造ブロブを再暗号化（新IV）し、メタJSONへアトミック保存する**。「再ロック時にまとめて確定保存する」方式は、確定前にクラッシュすると当該セッション中の全構造変更が失われるため採用しない。個々のメモ本文の保存（`.txtenc` への書き戻し）は既存の `crypto:saveEncrypted` 相当のフローをそのまま使う。
- **起点ノード自身のリネーム（レビュー指摘反映・明確化）**: セッション中に起点ノード自身の表示名を変更した場合、上記と同じ規律で即座にブロブ内の `realMemoName` を更新→再暗号化→メタJSONへアトミック保存する（他の構造変更と同一の扱いであり、特別扱いしない）。

### 1.6 メタJSON上のデータ構造（設計案）

`MetaTreeNode` に、ロック中のノードを表す専用の分岐を設ける（型定義自体は developer が `docs/data-model.md` / `src/shared/models.ts` へ正式反映する。以下は設計意図を示す案）。

```jsonc
// 通常ノード（現行 MetaTreeNode と同一）
{ "memoName": "買い物メモ", "expanded": true, "children": [ /* ... */ ] }

// ロック中ノード（子は必ず空。実体の構造はすべて lock ブロブの中）
{
  "memoName": "a3f9c1e2b7d4",     // 実ファイル名（難読化名）をそのままプレースホルダとして使う。
                                    // 表示は memoName を使わず、node.lock の有無で常に「🔒(ロック中)」とする
  "expanded": false,
  "children": [],                  // ロック中は常に空。実体は lock.blobCiphertextB64 の中
  "lock": {
    "kdf": { "algo": "scrypt", "N": 32768, "r": 8, "p": 1, "keyLen": 32 },
    "saltB64": "...",
    "ivB64": "...",                // ブロブ暗号化用の IV。書込のたび新規生成（.txtenc と同じ規律）
    "tagB64": "...",
    "hint": "...",                 // 任意。既存 .txtenc の hint と同じ「平文保存の旨」注意表示が必要
    "blobCiphertextB64": "..."     // 復号すると { realMemoName, children: MetaTreeNode[], nameMap: {realName: fileToken} } 相当のJSON
  }
}
```

- `lock` フィールドが存在するノードは、UIでは常に `memoName` を無視し「🔒(ロック中)」として描画する（`memoName` は実ファイル名参照専用の内部値）。
- ロック解除中（セッションが張られている間）は、上記 `lock` を持つ永続表現の代わりに、メインプロセスが構築した実行時ツリー（`TreeNode[]` 相当、実名で復号済み）をレンダラへ返す。これは既存の「メタ＝永続化専用 `MetaTreeNode` / 実行時＝`TreeNode`」の分離パターン（[docs/data-model.md](../data-model.md) §1）の自然な延長で扱える。
- **ブロブのサイズについて（レビュー指摘反映・許容事項の明記）**: ロック対象配下に非常に多くの子ノード（例: 1000件規模）がある場合、`blobCiphertextB64` 自体（子ツリー構造をまるごとBase64化したもの）が数MB規模になり得る。これは許容する。理由: 本アプリは元々「タブ全体のメタJSONを1ファイルとして起動時に丸ごとメモリへロードする」設計（[DESIGN.md](../../DESIGN.md) §3.2）であり、ノードロックの有無に関わらず巨大なツリーを持つタブは元々同種のコストを払っている。ノードロックのためだけにページング等の特別な最適化は行わない。

### 1.7 既存機構への対応（確定＋新規拡張）

- **全文検索インデックス**: ロック中はそのノード配下を**名前ごと**索引から除外する（現状は本文のみ除外なのでここを拡張）。**（確定・Q1）ロック解除中（セッション中）も配下メモの名前をインデックス対象から除外し続ける**（含めない）。理由: 既存M6の「暗号化メモは開封中かどうかに関わらず本文を常にインデックス対象外」という原則（DESIGN §2.4、復号平文の露出最小化が目的）と一貫させる。ロック解除セッション中の検索は、展開されたツリーを目視で探す運用で代替する。本文は既存原則がそのまま適用されるため、ロック解除の有無に関わらず常に除外のままで変更なし。
- **ファイル監視(chokidar)・自己書き込み予約**: 難読化後のファイルパスを基準に、既存の仕組み（`registerSelfWrite`/`consumeSelfWrite` パターン）をそのまま使える。パス解決に「本来名→実ファイル名」変換を挟むだけでよい（ロックセッションが持つ対応表がこの変換表を兼ねる）。
- **`.bak` バックアップ**: 既存の `atomicWrite` 機構をそのまま使う（難読化後のファイルパスに対して従来通り適用）。§1.6 の `lock` ブロブを含むメタJSON自体も既存のメタJSONアトミック保存・`.bak`世代管理の対象範囲内（[DESIGN.md](../../DESIGN.md) §2.6）でそのまま扱える。
- **メタ破損復旧カスケード（[00-core-principles.md](../00-core-principles.md) §9）との関係（確定・Q3）**: メタJSON本体と直近 `.bak` の両方を同時に失った場合、フォールバックの「フォルダ直下実ファイルからフラット構造でメタ再生成」が働くが、ロック中ノードの `lock` ブロブ（名前対応表そのもの）もこのタイミングで失われる。この場合、配下の実ファイル（難読化名の `.txtenc` 群）自体はディスク上に残り続けるが、**元の名前・親子関係との対応付けが永久に失われる**（パスワードが分かっても、どの実ファイルがどのメモだったか特定できなくなる）。**この一点故障は許容し、対応表の追加冗長化は行わない**。理由: 既存の「メタ喪失時はツリー構造を失うが本体は失われない」という受容済みトレードオフ（DESIGN §3.2）の延長線上であり、専用の副次バックアップ機構を新設するコストに見合わない稀なケースのため。
- **AutoReName**: 既存原則「暗号化メモ（`.txtenc`）は AutoReName 対象外」（[DESIGN.md](../../DESIGN.md) §2.2）がそのまま適用される。ロック対象配下のメモはロック解除中セッションであっても実ファイルは常に `.txtenc` のままのため、この既存ルールの単純な延長として **AutoReName は常に対象外**（手動リネームのみ）とする。
- **`memo:` リンク（確定・Q6）**: ロック中のノード配下を指す `memo:` リンクは**常に「何もしない」（未解決）扱い**にする。ロック解除セッションが有効な間は通常のリンクと同様に解決・遷移できる。理由: ロックの目的が「配下の存在自体を隠す」ことにある以上、ロック中は常に未解決という単純なルールにすることで挙動の一貫性を保つ（既存の「暗号化メモは開封を要求してから遷移」パターンとも整合する）。**全文検索が常に配下名を索引から除外し続ける（上記）のに対し本リンクはセッション中に解決できる点は一見矛盾するが、検索は「名前を知らない第三者への発見防止」が目的、リンクは「既に名前を知る本人による認証済みセッション内の追跡」であり目的が異なるため矛盾しない（設計意図の明記）。**
- **既存メタ書き込みとの競合について（レビュー指摘反映・明確化）**: ロックセッション中の構造変更（§1.5）は「最新のメタJSONを読込→当該ノードを更新→アトミック保存」という、既存の全ての構造変更IPC（リネーム・削除・移動等）と全く同じ read-modify-write パターンに従う。本アプリは単一ユーザー・単一プロセスのローカルアプリであり、同一タブに対する2つの構造変更操作が極めて短時間に重なった場合の「後勝ち」（先の変更が上書きされる）という特性は、ノードロック固有の新しいリスクではなく、既存v1の全ての構造変更操作が元々持つ特性をそのまま継承するものである。ロックブロブが1ノード分の変更を丸ごと1フィールドとして持つ点で「粒度が粗い」のは事実だが、影響範囲は他の構造変更操作と同等であり、v3のためだけに新しい競合解決（楽観ロック等）を導入する必要はないと判断する。

### 1.8 パスワードを忘れた場合（確定）

- 既存の暗号化メモと同じ「バックドアなし＝復旧不能」方針を踏襲する。この場合、名前も内容も両方失われる。UI上で明示し、ロック設定時に警告する。

### 1.9 Explorerから見た場合の見え方（確定・ユーザー合意済み）

- タブフォルダ自体は普段通りの1フォルダのまま（専用の隠しフォルダ等は作らない）。
- ロック対象配下のファイルは、無作為名の `.txtenc` としてフォルダ直下に並ぶ。
- `.tabtreenote.json` はタブ全体で1ファイルのため、ロックしていない他メモの名前・階層は普段通り見える。ロックした部分だけ暗号化ブロブ1つになる。
- **合意済みの残存リスク（対応不要）**: `.txtenc` 拡張子から「暗号化された何かがある」こと自体は推測できる／無作為名ファイルの個数は数えられる／メタJSON内に「ロック区画が1つある」という構造は見える。完全な痕跡ゼロ（ダミーファイル生成等の偽装）は不要。
- **複数のロック中ノードが同じ表示になる点について（レビュー指摘反映・意図的な仕様と明記）**: 同一タブ内に複数のロック中ノードがある場合、ツリー上はすべて同一の「🔒(ロック中)」表示になり、パッと見て区別がつかない。これは不具合ではなく**意図した挙動**である。ロック中ノードの表示名を区別可能にする（例: 一部だけ実名を見せる、任意のラベルを付けられるようにする等）と、それ自体が「名前に関する情報の部分的な漏洩」になり、§1.2の「起点ノード自身の名前も含めて秘匿する」という確定方針と矛盾する。区別が必要な場合は、ツリー上の位置（どの階層のどの順番にあるか）で判別するか、それぞれロック解除して中身を確認する運用になる。

### 1.10 サブツリーロックとM6個別暗号化の関係（確定・Q2）

ロック対象範囲に、既にM6の個別パスワード暗号化がかかったメモ（`.txtenc`）が混在する場合は、**ロック設定操作をエラーとする**（「暗号化済みのメモが含まれています。先に個別の暗号化を解除してください」と案内し、先に個別解除を求める）。パスワード体系の二重化（個別パスワード／ノードロックパスワードの両方が必要になる状態）や、既存の個別暗号化を黙って解いて包み直す重い暗黙操作は避け、最も単純で事故の少ない方式を採る。

### 1.11 UI操作・セッションの寿命（確定・Q4/Q5、レビュー指摘反映で追記）

- **操作導線**: 既存M6の暗号化設定/開封UIに準拠する。ツリー右クリックメニューに「サブツリーをロック」「ロックを解除」を追加し、既存の暗号化パスワード入力ダイアログと同じ見た目・確認再入力ルールを流用する。
- **複数ノードの同時ロック解除セッション**: 独立して許可する（既存の `sessionKeyStore` が `(tabId, memoName)` 単位で複数セッションを扱える仕組みの自然な延長）。
- **自動再ロック（時間経過によるタイムアウト）**: 設けない。時間ベースのタイムアウトは「何分でロックするのが適切か」という新たな調整項目を増やすだけで、後述のタブ切替時再ロックほど明確な区切りにならないため見送る。
- **セッションの寿命（確定、変更経緯は§5第3回参照）**: ロックセッションは以下のいずれかで終了する。(a) 明示的な再ロック操作、(b) **そのタブから離れる（別タブを選択する）**、(c) そのタブが登録解除される（`tab:remove`）、(d) アプリ終了。
  - 理由: ノードロックはM6個別暗号化（1メモの本文のみ復号保持）と異なり、**サブツリー丸ごとの名前・階層構造という、より広い範囲の情報**を復号状態でメモリに保持する。タブを離れている間はどの道その内容は画面に表示されないため、他のタブを操作している間まで復号状態を保持し続ける実利は乏しく、離席時の肩越し閲覧等のリスクを早めに閉じる方を優先する。
  - 同じタブ内で他のノードを操作している間（タブ自体は切り替えていない）はセッションは継続する。
  - **セッション破棄時の未保存編集の扱い（確定・2026-07-27訂正: 実装との差異を反映）**: ロック解除中の配下メモは実ファイルが`.txtenc`のため、`requestCloseCurrentMemo`（`App.tsx`）の分岐上は既存の暗号化メモ（M6）の未保存編集フローがそのまま適用される。すなわち、dirty状態のままタブを切り替えようとした場合、**平文メモ用の破棄確認ダイアログ（自作`ConfirmDialog`、「未保存の変更があります。破棄して別のメモを開きますか？」）は表示されず**、暗号化メモ（M6）と同じ「無確認で破棄しない＝dirtyなら自動保存してから処理を続ける」という既存方針（DESIGN §2.9）がそのまま適用される。実際のタブ切替が確定した**後**に、当該タブのロックセッション（対応表・復号済み構造）を破棄する（順序: 自動保存→タブ切替→セッション破棄）。ノードロック専用の新しい確認ダイアログは追加しない（既存の暗号化メモの仕組みがそのまま適用範囲を包含するため）。
    - 【訂正の経緯】当初（2026-07-25、第4回外部AIレビュー反映時、§5参照）は「既存の未保存編集確認フロー（`window.confirm`）」という表現で、平文メモと同じ破棄確認ダイアログが表示されることを想定していたが、M9c実装完了後のtester検証（2026-07-26）で、実装は`om.encrypted`（実ファイル拡張子由来）で分岐しており、ロック解除セッション配下は暗号化メモ側の「自動保存優先・確認ダイアログなし」の経路に入ることが判明した（実装当時の判断はDESIGNv3の趣旨と矛盾しないM6既存方針の自然な延長であり、実装ミスではない）。データは失われず（破棄ではなく自動保存されるため）Low・非ブロッキングと判断し、2026-07-27ユーザー判断で「コード変更はせず、本節の記述を実装に合わせて訂正する」方針（案A）で確定した。なお「`window.confirm`」という記述自体も既に古く（M2-R1-01対応で非ブロッキングな自作`ConfirmDialog`へ統一済み）、本訂正で合わせて修正した。

### 1.12 ロック境界をまたぐ移動・コピー（確定・ユーザー指摘反映で「一方通行の金庫」方式に変更）

ロック解除セッション中のサブツリーに対して、ドラッグ&ドロップ等で境界をまたぐ操作を行った場合の挙動。**ロック中（セッション無し）は§1.1の「あらゆる構造変更操作を禁止」がそのまま適用されるため、配下へのドラッグイン/ドラッグアウト自体が発生し得ない（対象を選択できない）**。以下はセッションが有効な間の挙動。

**採用方針**: **一方通行の金庫方式**を採用する。ドラッグ操作は事故（うっかり保護対象を外へ動かし自動で平文化されてしまう等）のリスクがあるため、保護範囲から平文の状態で出られる経路を一切作らない（変更経緯は§5第3回参照）。

- **移動・コピーとも「外→ロック解除中の配下へ」は許可する**: 移動・コピーいずれも、対象ノード（を根とする部分木）を**ロックセッションの鍵で暗号化・難読化名リネーム**し、対応表・子ツリー構造ブロブへ組み込む。ただし移動/コピー元に既存M6個別暗号化済み(`.txtenc`)のメモが含まれる場合は、§1.10と同じ理由で**エラーとし操作自体を拒否する**（先に個別解除を求める）。
- **移動・コピーとも「ロック解除中の配下 → 外」は共に禁止する**: 保護範囲に一度入ったものを外へ出す唯一の手段は**削除**とする（自動的な平文化・持ち出しの経路を一切作らない。個別の「暗号化解除して取り出す」ような迂回路も設けない＝一方通行を徹底する）。ドラッグ&ドロップでの境界外への移動操作自体をUI側で無効化する（ドロップを受け付けない）。
- **本方式は意図的に不可逆な制約であることの明記（確定・第4回反映）**: 「一方通行の金庫」方式は実装上の制約ではなく、**設計上意図した恒久的な制約**である。ロック解除セッション中であっても、ロック配下から平文の状態で取り出す手段（一時的な解除・エクスポート・迂回コピー等）は将来的にも一切設けない方針とする。配下から要素を除去する唯一の手段は削除（完全消去）であり、「元に戻す/取り出す」操作は仕様として提供しないことを、UI文言（右クリックメニューの説明・ドロップ拒否時のフィードバック等）でも明示する。

### 1.13 Markdown機能（§2）との交差ケース（確定・2026-07-26 designer追記）

M10a実装完了後のreviewer/tester検証で、ノードロック（本§1）とMarkdown保存形式（§2、`format: 'plain'|'markdown'`）の交差が未検討だったギャップが発覚した。ユーザー判断で「M10b（装飾ライブプレビュー）着手前にdesignerが設計を確定させる」こととし、以下の通り確定する。**本節は§1（ノードロック）と§2（Markdown）の両方に関わる横断的な節のため、便宜上§1側に置く。**

**発覚したギャップ**: `lockNode`（ノードのロック実行）・`writeSessionMemoContent`（セッション配下メモの保存）・`moveIntoSession`（「外→内」境界跨ぎ移動・コピー、§1.12）のいずれも、対象メモの元拡張子（`.txt`/`.md`）から判定される`format`を一切引き継がずに`.txtenc`化していた。「一方通行の金庫」方式（§1.12）のため、ロック配下に一度入ったメモが平文の拡張子へ戻る経路は無く、`format`を保持する手段が実装上どこにも存在しなかった（`NodeLockBlob`/`NodeLockSessionEntry`にも該当フィールドが無い）。この結果、`.md`メモを含むサブツリーをロックすると、そのメモが「Markdownメモである」という情報が失われ、ロック解除セッション中に開いてもM10bのライブプレビュー対象と判定できなくなる。

**追加で判明した関連ギャップ（ノードロックとは独立）**: 調査の過程で、既存M6個別暗号化（`crypto:open`）にも同種のギャップがあることが判明した。`SessionKeyEntry.format`（`src/main/crypto/sessionKeyStore.ts`）はM10a時点で既にメインプロセス側では`format`を保持しているが、`crypto:open`のレスポンス型`CryptoOpenResult`に`format`フィールドが無く、レンダラへ一切伝わっていない。これはノードロックの有無に関係なく、「暗号化された`.md`メモを個別開封した場合にライブプレビューが効かない」というM10bのゴール未達成につながるため、本節の一部として併せて修正する（推奨案として採用。設計判断の詳細な理由は下記「伝播の設計」参照）。

**伝播の設計（確定）**:

1. **ノードロックセッション配下の`format`保持先**: `NodeLockSessionEntry`（メモリ上のセッション状態）と`NodeLockBlob`（ディスク上の暗号化ブロブの中身）の両方に、`nameMap`と対になる`formatMap: Record<string, 'plain' | 'markdown'>`（realName→format、起点ノード自身の分も含めnameMapと同じキー集合）を新設する。**理由（採用案）**: 既存の`SessionKeyEntry.format`（M6個別暗号化の開封セッションが、開封時に`.txtenc`ヘッダから読み取った`format`をメモリ上にキャッシュし、以後の`crypto:saveEncrypted`ではファイルを読み直さずそのキャッシュ値を使い回す設計、`sessionKeyStore.ts`参照）と全く同じパターンを踏襲できる。代替案（各メンバーの`.txtenc`ヘッダの`format`フィールドのみを真実源とし、`eol`と同様に都度読み直す）は新しいMap構造が増えない利点はあるが、内容だけの保存（`memo:save`のlockContext分岐）のたびに「現在のformatを保全する」ため既存ファイルを読み直す一手間が全save経路に必要になり、`sessionKeyStore`が確立済みの「開封/生成時に一度だけ決定し、以後はメモリの値をそのまま使い回す」という既存パターンから外れる。よってformatMap案を採用する。個々のメンバー`.txtenc`ファイル自身のヘッダにも`format`は書いておく（自己記述性のための多重化、`eol`と同じ扱い）が、セッション内のロジックは常に`formatMap`（およびその永続化先である`NodeLockBlob.formatMap`）を唯一の真実源として参照する。
   - `formatMap`は`nameMap`と同じライフサイクルで管理する: 新規作成時（`memo:create`のlockContext分岐、args.formatから決定）に追加、「外→内」移動時（`moveIntoSession`、移動元の実`format`を引き継ぐ）に追加、リネーム時（`nameMap`と同様にキーだけ移し替え）、削除時（`nameMap`と同様に除去）、複製時（`nameMap`と同様に複製元の値をコピー）。
   - 保存（`memo:save`のlockContext分岐、内容のみの変更）は`formatMap`の値を変更せず、既存の値を`writeSessionMemoContent`へそのまま渡す（読み直し不要）。
   - 入れ子ロック（既にセッション内にあるメモをさらにロックする、§1.5/PLANv3 §7.4）の場合、新しいロックの`formatMap`は親セッションの`formatMap`から該当エントリを引き継ぎ、親セッション側からは（`nameMap`と同様に）除去する。
   - 後方互換: `NodeLockBlob`に`formatMap`が無い（本変更前に作られたテスト用ブロブ等）場合は空の`{}`とみなし、個々のlookupは未登録時`'plain'`扱いにフォールバックする（`TxtEncFile.format`省略時の既定と同じ扱い）。

2. **レンダラへの`format`伝播先（TreeNode経由、確定）**: `TreeNode`（`src/shared/models.ts`）に`readonly format?: 'plain' | 'markdown'`を新設する。既存の`editor`（メモ毎エディタ設定）と同様、「メモ本文そのものではなくメモに付随するUI用メタ情報」という扱いのため、`MemoReadResult`/`MemoSaveArgs`ではなく`TreeNode`側に持たせる（レンダラは既にツリー状態から`memoName`単位で`editor`/`label`等を引いている既存の実装パターンをそのまま踏襲でき、`memo:read`/`memo:save`の型を変更せずに済む）。
   - 通常領域（非ロック）の平文メモ: `tab:openTree`の突合処理（`metaStore.ts`の`reconcile`）が、走査結果`ScannedMemo.format`（既存M10a実装で既に取得済み）からそのまま設定する。
   - ロック解除セッション配下（起点＋子孫、非入れ子ロック）: `nodeLockSessionStore.ts`の`buildOriginTreeNode`/`buildSessionTreeNodes`が、上記1で新設する`formatMap`から設定する。
   - **通常領域の暗号化済み（`.txtenc`、未開封）ノード、およびノードロックの入れ子ロック済み（未解除）プレースホルダ**: `format`は`undefined`のままにする（意図的）。理由: これらは真の`format`がパスワード入力による復号を経て初めて判明するため、走査だけの時点（`scanTabFolder`は`.txtenc`の中身を読まない）で分かる情報ではない。`ScannedMemo`が暗号化ファイルに対して返す`format:'plain'`は実体を反映しない便宜上のプレースホルダ値であり、これをそのまま`TreeNode.format`へ転記すると「実は`.md`なのに`.txt`扱い」という誤情報をレンダラに渡してしまうため、明示的に「不明」（`undefined`）として扱う。
3. **レンダラへの`format`伝播先（M6個別暗号化の開封、確定）**: 上記の追加ギャップに対する修正として、`CryptoOpenResult`（`crypto:open`のレスポンス型）に`format: 'plain' | 'markdown'`（必須）を新設する。値は`sessionKeyStore`が既に保持している判定ロジック（`.txtenc`ヘッダの`format`、省略時`'plain'`）をそのまま転記する。レンダラは`crypto:open`成功時にこの値を「現在開封中のメモの format」としてローカルに保持し、ライブプレビューのON/OFF判定に使う（`TreeNode.format`が`undefined`のままの閉じた暗号化プレースホルダを、開封後にこの値で補う形）。
4. **セッション配下メモの拡張子変換（`memo:convertFormat`）は本節の対象外・現状維持**: M10a時点の既存方針（`lockContext`指定時は`NAME_INVALID`で明示的に拒否、`src/shared/ipc-contract.ts`の`MemoConvertFormatArgs`コメント参照）を変更しない。`formatMap`導入により技術的には「トークン名はそのままに`formatMap`の値だけ書き換える」形でセッション内変換を実装することも可能になるが、変換前確認ダイアログ等のUI導線はM10cスコープであり、本設計では対応しない（必要になった時点でM10c側の判断として再検討する）。

## 2. 機能2: Markdown＋ライブプレビュー

### 2.1 目的・編集体験（確定）

- **目的**: 文章の装飾（文字色・太字・文字の大きさ）と画像貼り付けに対応する。Markdown記法をユーザーに意識させない（非技術者を想定し、HTMLタグを直接書かせる方式は不採用）。
- **編集体験＝ライブプレビュー方式をデフォルトにする**（Obsidian/Typoraと同じ考え方）。CodeMirror 6を編集エンジンとして維持したまま、**装飾（デコレーション）機能**でMarkdown記法・許可されたHTMLタグをその場で実際の見た目（太字・色付き等）として表示しつつ、裏側の実データは常にMarkdownテキストとして保持する。
- **上級者向けの逃げ道**: 切替ボタンで裏の生Markdownソース表示にも切り替え可能にする。

### 2.2 装飾操作（確定）

- 右クリックメニューに「文字色」「太字」「文字の大きさ」等を追加し、選択範囲に対してクリックするだけで裏側に `<span style="color:...">` 等を自動挿入する。実装方式は既存の `src/renderer/editor/textCommands.ts`（選択範囲に対するテキスト変換コマンド群）と同様のパターンで、CodeMirrorの `changeByRange` を使い選択範囲をラップ/アンラップするコマンドとして追加する。
- 右クリックに気づかない人向けに、ライブプレビュー編集中専用のツールバーも用意する（配置・具体的なボタン構成は実装時にdeveloperが決めてよい技術的細部）。
- **Undo/Redoの粒度（レビュー指摘反映・明確化）**: 右クリックからの装飾操作（色/太字/文字サイズの適用）は、既存の`textCommands.ts`の各コマンドと同様に**1回の操作＝1回のCodeMirrorトランザクション＝Undo1回で完全に元に戻る**単位とする。独自のUndo管理は行わず、CodeMirrorの標準`history`拡張にそのまま乗る（既存パターンの追認であり新規実装は不要）。

### 2.3 安全性（確定、レビュー指摘反映で厳格化）

- 許可するタグを「文字装飾系（`<span>`）」と「画像挿入（`<img>`）」のみに絞った**許可リスト方式**で無害化する（DOMPurifyのようなサニタイズライブラリ、または自前の限定的な解釈器を想定）。
- **`style`属性は属性ごと許可するのではなく、CSSプロパティ単位で許可リストを設ける（レビュー指摘反映・厳格化）**: `style="color:...; font-size:...; font-weight:..."` のように、**`color`・`font-size`・`font-weight` の3プロパティのみ**を許可し、それ以外のプロパティ（`position`・`opacity`・`display`・`background`等）は値ごと除去する。理由: `style`属性を丸ごと許可すると`position:fixed`等による画面レイアウト崩し・要素の重ね合わせ悪用など、意図しない見た目改変の余地が生まれるため、実際に機能として提供する3項目（文字色・太字は`font-weight`・文字の大きさは`font-size`）に限定する。
- `<img>`は`src`（`data:image/...`のみ許可、外部URLは許可しない＝2.5節のBase64埋め込み方針と整合）・`width`・`height`属性のみ許可する。
- レンダラはサンドボックス化されている（`contextIsolation:true`/`nodeIntegration:false`/`sandbox:true`、[00-core-principles.md](../00-core-principles.md) §10）前提のうえで、**プレビュー描画時に許可リスト外のタグ・属性・CSSプロパティ（`<script>`・`on*` イベント属性・`javascript:` スキーム等を含む）を必ず除去する**ことをセキュリティ不変条件に追加する。装飾はあくまで見た目の変換であり、実行可能なコードを本文から生成させない。

### 2.4 保存形式・拡張子（確定・Q7）

- **新規拡張子 `.md` を導入する**（既存 `.txt` のまま一律適用はしない）。理由: (1) 既存 `.txt` メモの本文に偶然 `**強調**` や `<...>` のような文字列が含まれていた場合、一律適用すると意図せず装飾表示されてしまう下位互換性リスクを避けられる。(2) 既存の「暗号化状態の真実源は拡張子」という設計哲学（DESIGN §2.9）と対称的に「Markdown適用状態の真実源も拡張子」とすることで実装パターンを揃えられる。
- 新規メモ作成時に「通常メモ」「Markdownメモ」を選べるようにし、既存 `.txt` → `.md` への明示的な変換コマンドも用意する（M6の暗号化変換UIと同様のパターンを流用）。
- 保存形式自体はMarkdownテキスト（プレーンテキストの一種）のまま、現行の `.txt` と同じくポータブル性を維持する点は確定。
- **`.txt` → `.md` 変換時の扱い（レビュー指摘反映・明確化）**: `.txt` はそもそも画像埋め込み・装飾記法という概念を持たないため、変換時に本文へ手を加える必要は無い（拡張子とメタ情報の変更のみ。本文はそのままMarkdownソースとして扱われる）。移行すべき「既存画像」は存在しない。
- **`.md` → `.txt` 逆変換時の扱い（確定、ユーザー再質問を受け警告を追加）**: 既存の暗号化⇔平文変換（`.txt`⇔`.txtenc`）が中身を一切変換せず表現形式だけを変えるのと同じ方針を踏襲し、**本文の内容は一切変換・除去しない**（拡張子とメタ情報の変更のみ）。したがって、既に文字色・太字等の装飾を適用済みだった場合、`<span style="color:red">重要</span>` のような文字列が**タグ記号ごとそのまま** `.txt` 内に残る（`.txt` はライブプレビュー適用対象外のため、変換後に開くと色は付かず、タグの記号列がそのまま文字として画面に表示される＝現行のソース表示モードで見えているのと同じ見た目になる）。画像のBase64データURIも同様にそのまま残る（＝巨大な文字列がそのまま本文に残る）。
- **変換前の警告（確定・ユーザー指摘反映で追加）**: `.md` → `.txt` への変換操作時、本文中に装飾タグ（`<span`等）または画像データURI（`data:image/`）を検出した場合は、変換実行前に「この操作を行うと、色などの装飾用タグや画像データがそのまま文字として表示されるようになります。続行しますか？」の確認ダイアログを表示する（既存の`ConfirmDialog`を使う軽量な実装で足りる）。検出しなかった場合（装飾を一切使っていないMarkdownメモ）は無警告で変換してよい。データの欠落が起きない最も単純な方式を維持しつつ、ユーザーが結果を予期できるようにする。自動でタグ除去する等の「賢い」変換ロジックは実装しない。

### 2.5 暗号化メモ(`.txtenc`)との関係（確定）

- **文字装飾**: 単なるテキストなので、既存の「本文全体をまとめて暗号化する」仕組みに無改造で乗る。
- **画像（暫定方針としてユーザー了承済み）**: 平文メモとは別扱いとし、Base64化して本文（Markdown）中に直接埋め込む（`<img src="data:image/png;base64,...">`。Markdownの`![]()`記法ではなく`<img>`タグ形式とする。理由はM10c実装時の設計判断を参照）。平文メモは従来通り画像を別ファイル保存＋パス参照とする。理由: 暗号化メモの隣に平文の画像ファイルが並ぶと暗号化の意味が薄れるため。
- **レンダラへの`format`伝播（確定・2026-07-26追記、詳細は§1.13）**: `crypto:open`で個別開封した暗号化メモがMarkdown（`.md`由来）かどうかをレンダラ（M10bのライブプレビュー判定）が知るため、`CryptoOpenResult`に`format: 'plain' | 'markdown'`を追加する（メインプロセス側は`sessionKeyStore.format`として既にM10a時点で保持済みだが、レンダラへ未伝播だったギャップの是正）。ノードロックのロック解除セッション配下についても同様の伝播が必要なため、`NodeLockBlob`/`NodeLockSessionEntry`/`TreeNode`側の設計と合わせて§1.13にまとめて記す。
- **暗号化コンテナ内での判別方法（確定・Q8）**: `.txtenc` フォーマット（[docs/data-model.md](../data-model.md) §3）に、既存の `eol` フィールドと同様の要領で **`format: 'plain' | 'markdown'` フィールドを追加する**（`.mdenc` のような新拡張子は作らない）。理由: 「暗号化状態の真実源は `.txtenc` という1つの拡張子」という既存原則をこれ以上増やさずに済み、`memoFileService`/`metaStore`/全文検索等の拡張子判定ロジックへの影響を最小化できる。

### 2.6 既存機能との相互作用（確定）

- **自動リンク認識との共存**（[DESIGN.md](../../DESIGN.md) §2.8: URL/メール/パス/`memo:`）: Markdownのリンク記法（`[text](url)`）は許可リストに**含めない**（§2.7参照）ため、既存の自動リンク認識との重複・干渉は発生しない。現状維持でよい。
- **全文検索（確定・Q11）**: 装飾用HTMLタグ（`<span style="color:red">`等）を含んだ生のMarkdownテキストは、**タグを除去（プレーンテキスト化）してからインデックス対象にする**。理由: ユーザーが検索するのは装飾タグではなく実際の文章内容であり、タグ込みのまま索引すると意図しないヒットや一致範囲のズレが発生する。**検索マッチの判定自体はタグ除去後のプレーンテキスト基準で完全一致とする**が、**ライブプレビュー画面上でのハイライト表示位置（プレーンテキストのオフセット→装飾済み表示上の位置への変換）は多少のズレを許容するbest-effort実装でよい**（レビュー指摘反映・明確化。CodeMirrorの位置マッピングAPIで通常は正確に変換できる見込みだが、タグの境界をまたぐ選択等の稀なケースで多少ズレても許容する、という基準を明記しておく）。`SearchHit`の`matchStart`/`matchEnd`（data-model.md §4）の具体的な変換実装はdeveloperに委ねる。
- **画像埋め込みのサイズ（確定・Q9、レビュー指摘反映＋ユーザー指摘反映で表現を明確化）**: **推奨サイズの上限を設けて警告するが、保存自体は禁止しない**（目安: 1画像あたり数百KB〜1MB程度を超えたらUI側で警告表示するのみで、警告後にユーザーが続行を選べば保存は許可する。アプリ側でサイズを理由に強制的に貼り付け・保存を拒否するハードリミットは設けない）。**警告メッセージには実際に検出した画像サイズを明記する**（確定・ユーザー指摘反映）: 「この画像は約2.3MBです。挿入すると動作が重くなる可能性があります。挿入しますか？」のように、貼り付けようとしている画像の実際のバイト数（またはKB/MB換算値）を計算して表示する（貼り付け時点で画像データは既にメモリ上にあるため、追加のI/Oコストなく計算できる）。理由: 全文検索は起動時に全メモをメモリへロードしてインデックス化する方式（DESIGN §2.4）のため、大きなBase64文字列の混在は起動時間・メモリ使用量を悪化させるが、ユーザー自身が具体的なサイズを見た上で判断できれば十分であり、ブロックする必要はない。

### 2.7 許可するMarkdown記法の範囲（確定・Q10）

**「文字装飾（色・太字・文字サイズ）＋画像挿入」に絞り、見出し・箇条書き・Markdownリンク記法（`[text](url)`）等の構造記法は対象外とする。** 理由: HANDOFF.mdに記載された目的が「文章の装飾と画像貼り付け」に限定されており、構造記法まで広げるとスコープが拡大しすぎるため。将来的に構造記法を求める場合は別途相談する。
